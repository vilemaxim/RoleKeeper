# Project Context: RoleKeeper

## 🎯 Overview
RoleKeeper is a generic helper application for LARPs (Live Action Role-Playing
games). It provides character management, event/death tracking, and integrations
that work across many different LARP systems rather than being tied to one
ruleset.

## 🏗️ Core Architecture: Multi-Tenant by Design
The single most important thing to understand before touching the code:

**One application instance serves many LARPs simultaneously (multi-tenant).**

- Each LARP is a tenant with its own data, rules, and members.
- Each LARP has **organizers** who hold top-level permissions. Organizers:
  - Set up integrations (e.g. LarpManager)
  - Choose which rules the LARP uses
  - Set permissions for other users within that LARP
- Regular users operate within the permission scope an organizer grants them.
- Data access is scoped by tenant — code and Firestore rules must never let
  one LARP's users read or write another LARP's data.

When designing or implementing anything, always ask: "Which tenant does this
belong to, and what permission level does the acting user have within it?"

## 🧱 Stack
- **Frontend**: Flutter (Dart) — `lib/`. Tests in `test/`.
- **Backend**: Firebase Functions (TypeScript) — `functions/src/`. Tests are
  `*.test.ts`, run with `node --test`.
- **Database**: Firestore. Security rules in `firestore.rules`.
- **Storage**: Firebase Storage. Rules in `storage.rules`.
- **Auth**: Firebase Auth.
- **CI/CD**: GitHub Actions — CI (lint+test) gates PRs; CD deploys to Firebase
  on merge to main; a third workflow deploys Flutter web to GitHub Pages.

## 📂 Key Areas of the Codebase
- `lib/screens/` — Flutter UI screens
- `lib/services/` — business logic and Firestore access (follow existing
  patterns here when adding new data operations)
- `lib/models/` — data models
- `lib/utils/` — helpers (game paths, parsers, QR scanning, etc.)
- `functions/src/larpmanager/` — the LarpManager integration (a major external
  integration; has its own client, sync, auth, and types)
- `functions/src/gameTenant.ts` — tenant-related functions

## 🔁 Development Workflow (Planner → Worker)
This project separates planning from execution:
- **Planning**: An architect/planner session (Cursor architect rule) turns a
  rough idea into role-typed task files in `docs/tasks/ready/`. Human approves
  before anything enters the queue.
- **Execution**: A worker session picks up tasks via the `rolekeeper-tdd` MCP
  server, which enforces a TDD loop (test → implement → refactor) and runs
  `scripts/lint.sh` + `scripts/test.sh` at each phase. The worker hands off git
  commands; the human commits, opens a PR, and merges.

## ⚠️ Known Gotchas
- **Tenant isolation is paramount** — the biggest risk in this codebase is code
  that accidentally crosses tenant boundaries. Always scope by LARP.
- **Permission checks** — organizer vs regular-user permissions matter for
  almost every write operation. Don't assume a user can do something.
- **Firestore rules are effectively the backend security layer** — since the
  Flutter client talks directly to Firestore for many operations, security
  rules changes must ship alongside the features that depend on them.
- **Offline behavior exists** — some features (e.g. death timers, TOTP-based
  interventions) have offline paths. Changes here need offline test coverage.
- **The human owns git** — agents never push or merge. They output git
  commands for the human to run.
